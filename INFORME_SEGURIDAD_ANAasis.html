⚠ CONFIDENCIAL — CONTIENE HALLAZGOS DE SEGURIDAD SENSIBLES ⚠

1. Resumen Ejecutivo

La auditoría identificó 6 hallazgos de seguridad en el código fuente de la aplicación ANAasis: 1 crítico, 2 altos, 2 medios y 1 bajo.

El riesgo más urgente es la combinación de una clave de API hardcodeada en el bundle distribuido públicamente con un sistema de autenticación basado únicamente en número de teléfono. Juntos, estos dos defectos permiten que cualquier persona que descargue la app pueda consultar el historial médico, prescripciones y signos vitales de cualquier paciente conociendo solo su número de teléfono.

Dado que la aplicación maneja datos de salud sensibles (signos vitales, prescripciones, historial médico, ubicación GPS) de pacientes reales, se recomienda tratar los hallazgos críticos y altos como bloqueadores para producción.

3. Detalle de Hallazgos

F-01 — Clave de API hardcodeada en el bundle del cliente

Severidad: CRITICO

Archivos afectados:

  • src/app/core/services/user.ts — lineas 27, 72
  • src/app/core/services/medical.ts — 12 ocurrencias
  • anaasis-connect-plugin/android/.../RecordatorioCastWorker.kt — linea 22

Descripcion:
La cadena "ANAASIS_2026" se usa como unica clave de autorizacion en todas las llamadas al API de anaasis.php. Al estar hardcodeada en el codigo fuente del cliente, queda compilada dentro del APK de Android y el bundle JavaScript. Cualquier persona que descargue la aplicacion puede extraerla en minutos usando herramientas publicas como apktool o inspeccionando el JS con las DevTools del navegador. 

// user.ts:27 y medical.ts (multiple)
api_key: "ANAASIS_2026"

// RecordatorioCastWorker.kt:22
private const val API_KEY = "ANAASIS_2026"

Impacto:
Con la clave extraida, un atacante puede llamar directamente a angelesmedic.com.mx/crm/api/anaasis.php con acciones como get_vitals, get_prescriptions, save_vitals, get_user_appointments para cualquier numero de telefono, sin ser usuario registrado.

Cambio requerido:

  1. Eliminar la clave estatica de todo el codigo cliente.
  2. En el login, el servidor debe emitir un token de sesion (JWT o token opaco con expiracion) ligado al usuario autenticado.
  3. Todas las llamadas subsecuentes deben incluir ese token en el header HTTP (Authorization: Bearer <token>), nunca una clave compartida.
  4. El servidor valida el token en cada peticion; si no es valido o expiro, responde 401 y el cliente redirige al login.
  5. Implementar rate limiting por IP en el servidor para limitar abuso en caso de que una clave o token sea comprometido.

F-02 — Autenticacion basada unicamente en numero de telefono

Severidad: ALTO

Archivos afectados:

  • src/app/core/services/user.ts — lineas 68–78
  • src/app/shared/components/login-modal/login-modal.component.ts

Descripcion:
El inicio de sesion envia al servidor unicamente el numero de telefono del paciente (y la clave de API compartida del hallazgo F-01). No existe contrasena, OTP ni ningun segundo factor de verificacion. 

// user.ts:68-78
const body = {
  action: "login_user",
  api_key: "ANAASIS_2026",
  phone: credentials.phone   // unico dato del usuario
};

Impacto:
Cualquier persona que conozca o adivine el numero de telefono de un paciente puede iniciar sesion como esa persona y acceder a su historial medico completo: signos vitales, prescripciones, citas medicas y ubicacion GPS.

Cambio requerido:

  1. Agregar verificacion por OTP via SMS al numero de telefono registrado como minimo viable de seguridad para una app de salud.
  2. Alternativamente, implementar contrasena real definida por el usuario en el registro (ver F-03).
  3. El servidor debe devolver un token de sesion unicamente si la verificacion es exitosa (resuelve tambien F-01).

F-03 — Contrasena provisional identica para todos los usuarios

Severidad: ALTO

Archivo afectado:

  • src/app/core/services/user.ts — linea 28

Descripcion:
En el flujo de registro, el cliente envia una contrasena hardcodeada identica para todos los pacientes que se registren en la aplicacion. 

// user.ts:28
password: "password_provisional_2026",  // mismo valor para TODOS los usuarios

Impacto:
Si el servidor llegara a implementar autenticacion por contrasena en el futuro, todos los usuarios existentes ya tendrian su contrasena comprometida. Ademas, cualquier atacante que extraiga el bundle conoce la contrasena de todos los pacientes registrados desde el inicio de operaciones.

Cambio requerido:

  1. Eliminar este campo del request de registro.
  2. Redisenar el flujo de registro para que el paciente defina su propia contrasena, o usar OTP (lo que resuelve tambien F-02).
  3. El servidor debe almacenar la contrasena como hash (bcrypt o Argon2), nunca en texto plano.

F-04 — Datos del paciente en localStorage sin cifrar

Severidad: MEDIO

Archivos afectados:

  • src/app/core/services/user.ts — lineas 45–61
  • src/app/home/home.page.ts — lineas 308, 328, 359, 854

Descripcion:
El perfil del paciente (nombre, telefono, patient_id) se persiste en localStorage del WebView en formato JSON sin ningun cifrado. 

// user.ts:45
localStorage.setItem(this.USER_KEY, JSON.stringify(profile));
// Clave: 'anaasis_user_data' — visible en texto plano

Impacto:
En un dispositivo Android rooteado, o ante acceso fisico al dispositivo, los datos del paciente son legibles directamente desde el sistema de archivos sin necesidad de conocer ninguna credencial. Para una aplicacion de salud este dato es suficiente para realizar ataques de enumeracion sobre el API (ver F-01 y F-02).

Cambio requerido:

  1. Reemplazar localStorage por @capacitor/preferences, que en Android usa EncryptedSharedPreferences respaldado por el Android Keystore.
  2. Actualizar todas las referencias directas a localStorage.getItem ('anaasis_user_data') en home.page.ts para usar el servicio User centralizado.

F-05 — Endpoint de alerta SOS sin autenticacion ni trazabilidad

Severidad: MEDIO

Archivo afectado:

  • src/app/core/services/medical.ts — lineas 53–60

Descripcion:
La funcion que dispara la alerta de ambulancia no incluye ninguna clave, token ni identificador del paciente. El endpoint sos_proxy.php recibe coordenadas GPS y datos del paciente sin verificar la identidad del solicitante. 

// medical.ts:53-60
enviarAlertaAmbulancia(lat, lng, detalle) {
  return this.http.post(`${this.API_URL}/sos_proxy.php`, {
    latitud: lat,
    longitud: lng,
    paciente: detalle
    // sin api_key, sin token, sin identificacion del usuario
  });
}

Impacto:
Cualquier actor que conozca el endpoint puede enviar alertas de ambulancia falsas con coordenadas y datos de paciente arbitrarios, sin dejar ninguna traza que permita identificar al responsable.

Cambio requerido:

  1. Incluir el token de sesion del usuario (una vez implementado en F-01) en el body o header de la peticion.
  2. El servidor debe validar que el solicitante es un paciente autenticado antes de procesar la alerta.
  3. Registrar en el servidor el identificador del paciente, IP de origen y timestamp en cada alerta SOS para trazabilidad.

F-06 — Inconsistencia: chat.php y doctors.php sin mecanismo de auth

Severidad: BAJO

Archivo afectado:

  • src/app/core/services/medical.ts — lineas 16–26

Descripcion:
A diferencia del resto de llamadas al API, las peticiones al chat y a la lista de doctores no incluyen ninguna forma de autenticacion (ni siquiera la clave estatica del resto del sistema). 

sendMessage(message: string) {
  return this.http.post(`${this.API_URL}/chat.php`, { message }); // sin nada
}
getDoctors() {
  return this.http.get(`${this.API_URL}/doctors.php`); // sin nada
}

Cambio requerido:
Una vez implementado el sistema de tokens de sesion (F-01), incluir el token en estas llamadas tambien. El chat en particular recibe mensajes de texto libre y deberia estar siempre asociado a un usuario autenticado.
